## What happened

`postprocess-reppo.sh` ran today's 4-intent batch (1 mint + 3 votes) for the 2026-05-31 1st-run. Mint and 2 DISLIKE votes (pods 466, 467) succeeded on-chain. The 3rd vote (pod 462 LIKE) reverted on dry-run, real write skipped:

```
- `vote-462-like.json` — **dry-run failed** (code: CANNOT_VOTE_FOR_OWN_POD), real write skipped
  - output: {"error":{"code":"CANNOT_VOTE_FOR_OWN_POD","message":"Simulation reverted","hint":"Publishers cannot vote on their own pods. Use a different voter EOA — set REPPO_VOTER_PRIVATE_KEY to a wallet that did not mint the pod."}}
```

Pod 462 was the agent's own 2026-05-30 11th-mint (tx `0x12ecfbdde461ef308963f2f30923bdabf8d3a90e11d4244d0177407f2a43cc11`, hash `06e7715d81cdedca`). Trading-agent's own summary called this out as deliberate ("first LIKE this run breaks ISS-005's all-DISLIKE pattern") — the LIKE on own pod was an explicit experiment driven by MEMORY.md's "Lessons Learned" line: *"Vote slot can be blocked by agent's own mint cadence — when current-epoch is owned entirely by your own prior mints, 'AND is NOT one you just minted' reads as '0 vote targets'. Worth a SKILL.md tighten on whether to LIKE-vote own mints or stay neutral."*

The answer is now empirically settled: own-mint LIKE-voting reverts deterministically. The trading-agent already gates on `pod 463` ("intentionally skipped to avoid double self-promo signal") — gate needs to be consistent across all own-pod ids regardless of direction.

## Impact

- 1 vote intent lost per occurrence; the pod-462 LIKE never reaches chain (intent file removed post-revert).
- Wastes 1 of the 3 vote_cap slots per run when current-epoch is dominated by the agent's own mints.
- Not destructive on-chain — dry-run gating in `postprocess-reppo.sh` catches it before real-write.
- Loud failure in `## Execution Results` so downstream digest catches it.

## Investigation paths / fix

1. **SKILL.md tighten (primary fix).** In `skills/reppo-trading-agent/SKILL.md` vote_filter, add explicit gate: exclude any pod-id whose publisher matches the agent's publisher address — regardless of intended direction. Apply consistently across the candidate pool, not just per-direction.
2. **Operator EOA split (alternative).** Set `REPPO_VOTER_PRIVATE_KEY` to a separate funded EOA that did not publish any of the existing 13 own-mint pods. Operator call — requires fresh wallet provisioning, veReppo lock, gas funding.
3. **Postprocess pre-flight (defence-in-depth).** Have `postprocess-reppo.sh` pre-filter own-pod votes before dry-run by reading the publisher field from `.reppo-cache/pods.json` against the configured publisher address — saves 1 dry-run round-trip per occurrence.

## Why medium

- Single intent lost per occurrence; non-destructive.
- 1 occurrence to date (2026-05-31), but structurally guaranteed to recur as long as the agent dominates current-epoch mints — own-mint dominance is exactly the condition that drove the experiment.
- Loud failure surface (no silent loss).
- Promote to high if recurrence rate >50% over the next 5 runs without fix.

## Recurrence: 2026-06-09 — 5 reverts in a single postprocess

Today's 1st-run produced 9 vote intents (2 LIKE / 7 DISLIKE) at epoch 103. Postprocess dry-runs failed CANNOT_VOTE_FOR_OWN_POD on **5 of 9** (55.6%):

```
- `vote-764-dislike.json` — dry-run failed CANNOT_VOTE_FOR_OWN_POD
- `vote-824-like.json`    — dry-run failed CANNOT_VOTE_FOR_OWN_POD
- `vote-825-dislike.json` — dry-run failed CANNOT_VOTE_FOR_OWN_POD
- `vote-828-dislike.json` — dry-run failed CANNOT_VOTE_FOR_OWN_POD
- `vote-832-like.json`    — dry-run failed CANNOT_VOTE_FOR_OWN_POD
```

Hit rate **crosses the >50% promote-to-high threshold** flagged in the original "Why medium" section.

Key change from 2026-05-31: this run's voter — not trading-agent — selected the pods. The voter's own-pods prefetch is at `count:0` for the **21st consecutive voter run** (per today's voter funnel report), and the ledger wallet-shortcode workaround MEMORY.md tracks as "durable" did **not** fire because:

- The 5 reverted pods reference wallets `0x3dd4..7a81` (pods 764/825/828/832) and `0x9984..95ba` (pod 824) — NOT our standard mint-wallet shortcodes (`0xecb6..2b00`, `0x944b..f123`, etc.). The ledger workaround only cross-references pod NAMES against past mint shortcodes; it has no signal on historical own-pods predating the ledger.
- The voter EOA (`0xb4EC..4c64`) is evidently the on-chain publisher of these older pods — minted off-ledger before 2026-05-26 (the ledger's first row).

So the workaround MEMORY.md called "durable" covers only ledger-tracked own-pods. The voter still has a blind spot for historical own-pods.

## Severity promote: medium → high

Recurrence pattern now structural (publisher EOA shared by trading-agent and voter overlaps historical Reppo platform mints predating the ledger) and rate-confirmed >50% on a single day. Promote on next read.

## Investigation paths / fix (updated)

1. **own_pod_ids prefetch repair (primary, now critical-path).** 21 consecutive voter runs at `count:0` — the underlying prefetch contract is broken. Fix it to return the actual publisher EOA's own-pod-ids on the Reppo platform; that will catch both ledger-tracked and historical own-pods in one pass. See MEMORY.md's "ISS-016 own_pod_ids prefetch repair" goal.
2. **Postprocess pre-flight (defence-in-depth, raised priority).** Have `postprocess-reppo.sh` pre-filter votes by reading the publisher field from `.reppo-cache/pods.json` against the configured publisher address — would have caught all 5 today before dry-run. Cheap, idempotent, no operator dependency.
3. **Operator EOA split (alternative).** Set `REPPO_VOTER_PRIVATE_KEY` to a separate non-publisher EOA — bypasses the issue entirely. Requires fresh wallet provisioning, veReppo lock, gas funding.
4. SKILL.md gate from original investigation still applies, just no longer the primary fix path (today's reverts came from the voter, not trading-agent).

## Recurrence: 2026-06-09 4th-run — exact replay of 1st-run reverts

The 3rd-run (midday) defensively cross-referenced the 1st-run digest and pre-skipped pods 764/824/825/828/832 — 0 reverts. The 4th-run (evening) **dropped that cross-ref**: the voter re-queued the same 5 pods (2 LIKE / 3 DISLIKE) per skill spec, flagging the prior-run reverts in its own note as "possible-but-unconfirmed" rather than load-bearing. Postprocess dry-runs (2026-06-09T12:35:43Z) failed CANNOT_VOTE_FOR_OWN_POD on all 5 — exact replay of the 1st-run pattern, same voter EOA `0xb4EC..4c64`.

This confirms the cross-ref workaround is not durable across runs without filesystem-persistent state — the voter cannot reliably "remember" the prior digest between independent runs. **Only the prefetch repair (path 1 above) fixes this.** Today: 2 runs reverted (1st + 4th) and 1 run defended (3rd) on the same 5 pods. Hit rate over the day on these 5 pods: 2/3 = 66.7% revert.

## Severity confirmed: high

Recurrence rate now 100% on first contact and 66.7% over 3 same-day runs without an operator fix to the prefetch contract. Severity stays high.
