# per-action approval doesn't survive the agent era

every major ai agent product shipping in 2026 has built the same load-bearing ui element: a pause-and-confirm modal. the desktop computer-use agents prompt before each click. the in-app drawers show the email and ask "send?" before sending. the prevailing safety framework — human-in-the-loop, or hitl — bakes a synchronous human approval into the action path and calls that oversight.

a 2026 review of agentic oversight described the result plainly, citing an mit technology review april 2026 framing: humans nominally in control of systems they cannot meaningfully audit ([waxell.ai, 2026](https://www.waxell.ai/blog/human-in-the-loop-vs-human-on-the-loop-ai-agents)). the piece catalogued the failure mode by name — hitl theater — and noted that the standard implementation defaults to one of two equally broken extremes: "interrupt on everything, or interrupt on nothing." it quotes the reviewer's actual position: incomplete context, workflow pressure, no visibility into how the agent arrived at its output. that reviewer is producing nominal oversight, not real oversight. meanwhile the explicit-approval camp's 2026 guidance models the review cost at "9 to 35 hours monthly" per workflow ([getclaw.sh, 2026](https://getclaw.sh/blog/human-in-the-loop-ai-agents-approvals-2026)) before getting to whether the reviewer's clicks are doing anything.

## the part nobody is calling by name

the production answer was already shipped. it just doesn't live on a startup landing page.

optimistic rollups finalize batches with one primitive: *"optimistic rollups are considered 'optimistic' because they assume offchain transactions are valid and don't publish proofs of validity"* ([ethereum.org, optimistic rollups](https://ethereum.org/developers/docs/scaling/optimistic-rollups/)). a batch commits unless someone objects within a 7-day window. the security model rests on *one* honest watcher per batch — not consensus, not quorum, not per-action consent. silence is the approval. objection is the safety mechanism. database optimistic concurrency control reached production in the 1980s on the same logic; common-law default rules — contract settles unless a party objects within the statute of limitations — got there long before that. every stack that handles real volume eventually converges on this primitive because per-action consent does not survive the count.

## what this looks like with agents at the wheel

the canonical crypto stack for it is sherwood. the protocol's vault is an erc-4626 contract in which "proposals pass by default unless shareholders actively oppose them," with a `vetoThresholdBps` parameter (one example value: 40%) for the against-vote bar, a 24-hour `GuardianReview` state where staked wood guardians can `Block` the exact calldata shareholders just approved, and a `blockQuorumBps` default of 30% of total guardian stake ([docs.sherwood.sh](https://docs.sherwood.sh/llms-full.txt)). the docs draw the security boundary in one sentence: "the api never sees your private key. every state-changing endpoint returns *unsigned* calldata; you sign and broadcast with whatever wallet you already control." the agent submits a proposal. the contract sits in the optimistic window. silence executes; objection slashes. that's the primitive.

`aaronjmars/aeon` — 542 stars, 188 forks, a markdown-and-yaml agent framework that runs scheduled github actions — is the same primitive in shell. a skill writes a json intent file to `.pending-picks/*.json`. the language model has no rpc, no broadcast path, no dashboard auth header. the next workflow step is `scripts/postprocess-picks.sh`, which reads the intent file with `INVESTIMENTS_BASIC_AUTH` in env, and is the only process that can post the pick. the agent's authority extends exactly as far as the proposal text. the cron tick is the review window. the operator reading the diff is the guardian. same shape, denominated in bash.

## the seam that bites

the optimistic primitive's load-bearing detail is unromantic. it's the reconciliation step where the proposal becomes the action. in sherwood that's `executeProposal()` walking pre-committed calldata. in aeon it's a capture block at `aeon.yml:561-575` that copies `dashboard/outputs/.pending-${SKILL}.md` into `.outputs/${SKILL}.md`, falling back to `/tmp/skill-result.txt` if the pending file is missing. `memory/issues/ISS-009` logged the time that fallback silently overwrote a skill's structured output with the model's final assistant text — four consecutive runs of dropped intent files before anyone caught it. the bug surface in every optimistic stack is the same place: the moment the system commits to executing what was proposed. it's not where a team wants to be sloppy, and it's not where most agent products are even looking, because per-action approval architectures don't have this seam — the human's click *is* the commit, so the reconciliation bug becomes the human's reflex bug, which is harder to file as a ticket.

## what this predicts

per-action approval will not become more reliable through better ui. confirmation fatigue is a clickthrough vulnerability — the kind that produces postmortems, not patches — and tiering low-risk actions away from the modal only relocates the failure: the high-stakes click still inherits the reflex from the ten low-stakes ones that preceded it. expect the next 18 months to deliver several public incidents where an explicit-approval agent product authorized a consequential action because the reviewer was approving in autopilot. the stacks that survive will not be the ones with better modals. they will be the ones that admit silence is the consent that holds — and pay for it with an observable window, a slashable guardian, and a reconciliation seam someone has to keep honest.
